## 三、發現事項（Findings）

### 發現 #1：長時間運行之 `next dev` 開發伺服器快取損毀，一度導致 `/seminar/0915/thanks` 回傳 500

- **現象**：以瀏覽器實測報名流程時，`POST /api/register` 正常回傳 200，但前端未導向感謝頁；直接訪問 `/seminar/0915/thanks?eid=...` 穩定重現 `500`，錯誤訊息為 `ENOENT: no such file or directory, open '.next/server/app/seminar/0915/thanks/page.js'`（該編譯產物缺失，但同目錄下 `/seminar/0915/page.js` 正常存在）。
- **根因判定**：**非原始碼缺陷**。以下兩項證據交叉確認：(1) 全新 `npm run build`（production build）可正常編譯 `/seminar/0915/thanks` 路由，型別檢查與靜態頁面產生皆成功；(2) 移除 `.next` 快取後重新啟動乾淨的 `npm run dev` 程序，該路由立即恢復 200，且完整重跑一次報名流程可正常導向感謝頁。研判為該開發伺服器程序已長時間運行（自更早的測試階段起，累積多次 Fast Refresh 熱更新），導致 dev 模式的 webpack/Turbopack 增量編譯快取進入不一致狀態，這是 Next.js dev 模式已知的一類穩定性問題（`next dev` 的 Fast Refresh 快取機制），與應用程式邏輯無關。
- **已採取行動**：本次測試中已重啟開發伺服器（`rm -rf .next` + 重新 `npm run dev`）排除問題並完成後續全部測項；未修改任何 `app/`／`components/`／`lib/`／`prisma/`／`middleware.ts` 原始碼。
- **建議**：正式進入 8/5–8/7 staging 測試窗口前，建議重新啟動一次 staging 服務程序；若 staging 環境是以 `npm run dev` 常駐運行（而非 `next build && next start`），建議評估改用 production 模式常駐（不含 Fast Refresh，無此類快取失效風險），或至少約定測試期間若遇到頁面異常先重啟服務再回報為缺陷，避免誤判。

### 發現 #2：測試資料尚未清理

- **現象**：本次測試依 CTO 文件「用可辨識的測試 Email」之規則，新增 4 筆測試報名資料（`test+qa-w1@example.com`／`test+qa-w2@example.com`／`test+qa-edm1@example.com`／`test+qa-idempotency@example.com`），加上測試前即存在之 1 筆（`test+w1@example.com`），資料庫目前共 5 筆皆為測試資料。
- **影響**：依文件本身規則「測完標記或刪除，別讓假資料混進報名人數」，這些資料在正式報名人數統計前必須排除。
- **限制**：`/admin` 後台**依規格刻意不提供刪除功能**（`admin-console` spec 明文要求），故無法透過後台介面清除，僅能由 CTO 直接於資料庫層（`prisma/dev.db`）操作，或於後續正式改用 Supabase 時以全新資料庫起始，一併帶過此問題。
- **建議**：8/5 測試窗口正式開始前，或在切換到 Supabase 之前，由 CTO 確認是否需要先清空本機 `dev.db` 目前的測試紀錄，避免與 8/5–8/7 期間的真實測試資料混淆難以區分。

### 發現 #3：中文參數經由本機 shell 內嵌字串傳遞會被污染（測試方法產物，非伺服器缺陷）

- **現象**：測試初期以 `curl -d '{"name":"中文..."}'`（inline 字串）或 `--data-urlencode "dept=中文值"` 方式送出含中文的請求時，回應與資料庫中的中文字元呈現亂碼（類似 Big5/CP950 誤判 UTF-8 位元組）。
- **根因判定**：確認為本機 Windows/Git-Bash 執行環境之字元編碼問題，**與伺服器無關**——改用 UTF-8 檔案（`--data-binary @file`）或瀏覽器內 `fetch()` 送出完全相同的中文內容後，資料庫儲存與回應皆完整正確（如 SUP-08 所列）。
- **影響**：無實際產品影響，僅記錄以說明本報告中若干測項改用檔案／瀏覽器 fetch 方式重測的原因，避免誤讀為系統缺陷。
